# Architecture Decision Records

One entry per decision the project plan does not spell out: what, why, what was rejected.

## ADR-001 - EKS 1.35 for the baseline cluster

- **What:** The baseline cluster runs Kubernetes 1.35 on EKS, with the AL2023 managed node AMI. The original workload was built on 1.30.
- **Why:** EKS no longer offers 1.30 in us-east-1 (`aws eks describe-cluster-versions`, checked 2026-10-16: oldest available is 1.31, in extended support). The workload installs Istio with istioctl 1.30.2, and Istio 1.30 supports Kubernetes 1.32 to 1.36 (istio.io supported releases page). The versions in EKS standard support are 1.34, 1.35, 1.36 and 1.37, so 1.34, 1.35 and 1.36 satisfy both. 1.35 stays in standard support until 2027-03-27, so it never bills the extended-support rate during the build, and it sits inside Istio's range rather than at its edge. Amazon Linux 2 node AMIs are not published for 1.33 and later, so the node group moves to AL2023.
- **Rejected:** 1.34 (standard support ends 2026-12-02, too close); 1.36 (the newest version Istio 1.30 supports, with no margin); 1.37 (outside Istio 1.30 support); upgrading Istio at the same time (two changes to the baseline instead of one).

## ADR-002 - Partial backend configuration kept out of git

- **What:** The stacks declare `backend "s3" {}` and load the bucket name from `infra/backend.hcl`, generated by the bootstrap stack and git-ignored. The bucket name uses a random suffix instead of the account ID. Locking uses S3 native lock files (`use_lockfile`), with no DynamoDB table.
- **Why:** The repository is public from day one, and backend blocks cannot use variables, so a literal bucket name would publish an account-linked identifier.
- **Rejected:** A bucket name built from the account ID (leaks the ID). A DynamoDB lock table (an extra resource, no longer needed since Terraform 1.10).

## ADR-003 - Bootstrap stack state stays local

- **What:** `infra/backend` keeps its own state on the build machine (git-ignored). It holds only the state bucket and the budget.
- **Why:** The stack creates the bucket the others store state in. Migrating its state into its own bucket adds a circular dependency for two resources that are destroyed last.
- **Rejected:** Migrating the bootstrap state into the bucket after creation.

## ADR-004 - Changes made to the original workload when copying it

- **What:** The baseline is the original platform with only these changes: Kubernetes 1.35 and AL2023 nodes (ADR-001); a partial S3 backend (ADR-002); provider default tags `Project=zero-trust`, with the original `Project` tag renamed `Workload` so it does not override it, and `Project` repeated on the EKS module tags so node instances carry it; a tag annotation on the Istio ingress gateway service so its load balancer is tagged; account-specific Helm values (ECR URLs, IRSA role ARNs, queue URLs) removed from the values files and injected at deploy time from Terraform outputs; the simulator reads its target from `API_BASE_URL` instead of a hardcoded load balancer hostname; comments, descriptions and log messages translated to English, emojis removed. Network layout, security groups, public ingress, NAT and IAM policies are unchanged.
- **Why:** The "before" measurement must describe the original exposure, so nothing that affects reachability is touched. The other changes are required to deploy in a new account, to tag every resource for cleanup verification, and to publish the code without account identifiers.
- **Rejected:** Redeploying the Prometheus, Grafana and Kiali sample addons: they are ClusterIP services that do not change the exposure being measured, and on two t3.medium nodes (the account allows 5 vCPU) their memory is better left to the workload and the security tooling added later.

## ADR-005 - Two retrofit switches in the baseline stack

- **What:** The baseline cluster stack gets two variables whose defaults are the original design: `cluster_endpoint_public_access` (true) and `enable_nat_gateway` (true). The retrofit sets the first to false. The second is decided by measurement in Phase 5. With the public API endpoint off, kubectl, helm and istioctl reach the private endpoint through a Session Manager port forward on a worker node (`scripts/k8s_tunnel.sh`).
- **Why:** The EKS endpoint setting and the NAT gateway belong to resources the baseline stack owns, so they can only change there. Everything new lives in `infra/zerotrust`.
- **Rejected:** Keeping the public endpoint restricted to one source CIDR (still a public listener, and the scan from that CIDR would still find it open). A bastion host (a standing entry point, the thing the project removes).

## ADR-006 - Two /1 routes instead of editing the module-owned default route

- **What:** The public subnets reach the internet through the firewall endpoint by two routes, 0.0.0.0/1 and 128.0.0.0/1, added to the module's public route table by the zerotrust stack.
- **Why:** The VPC module owns the 0.0.0.0/0 route to the internet gateway. Longest prefix match makes the two /1 routes win for every destination, without two stacks owning the same route. Destroying the zerotrust stack restores the original routing exactly.
- **Rejected:** Re-associating the public subnets with a new route table (the module owns those associations); forking the VPC module.

## ADR-007 - One firewall endpoint, in the NAT gateway's availability zone

- **What:** AWS Network Firewall gets one endpoint, in the availability zone of the single NAT gateway. Traffic from the second public subnet crosses zones to reach it.
- **Why:** The original design already has a single NAT gateway, so egress has one zonal point of failure either way. A second endpoint doubles the largest hourly cost of the stack (0.395 USD per endpoint hour in us-east-1).
- **Rejected:** One endpoint per zone, which is the production pattern and is noted as such.

## ADR-008 - DynamoDB Streams through its interface endpoint, by explicit URL

- **What:** fraud-detection reads the transactions stream through the `dynamodb-streams` interface endpoint, set with the standard SDK variable `AWS_ENDPOINT_URL_DYNAMODB_STREAMS` at deploy time.
- **Why:** `aws ec2 describe-vpc-endpoint-services` shows no private DNS name for this service, so without the variable the SDK resolves the public hostname and leaves through the NAT gateway. The variable needs no code change.
- **Rejected:** Allowlisting the public stream hostname in the firewall (traffic would still leave the VPC, and the IAM source-VPC condition would deny it).

## ADR-009 - Minimal Session Manager agent policy on the node role

- **What:** The node role gets an inline policy with only the agent registration, message and channel actions, plus write access to the session log group. `Resource = "*"` is used for the `ssm:UpdateInstanceInformation`, `ssmmessages:*Channel`, `ec2messages:*` and `logs:DescribeLogGroups` actions because they do not support resource-level permissions.
- **Why:** The managed policy AmazonSSMManagedInstanceCore also grants Parameter Store reads, which the nodes do not need (EKS best practices guide, infrastructure protection).
- **Rejected:** AmazonSSMManagedInstanceCore.

## ADR-010 - Network Firewall alerts reach Security Hub as custom findings

- **What:** A Lambda function subscribed to the firewall alert log group (filter: action blocked) imports one Security Hub CSPM finding per rule, source address, destination port and day, with `BatchImportFindings` into the account's default product. Its role can only import into that product and write its own log group.
- **Why:** AWS Network Firewall is not an integration that sends findings to Security Hub CSPM. The official list of AWS services that send findings (Security Hub CSPM user guide, "AWS service integrations") contains Firewall Manager, but only for WAF and Shield Advanced findings. Without this function, Security Hub would show no trace of a blocked attempt.
- **Rejected:** Claiming a native integration; routing the firewall through Firewall Manager (it needs AWS Organizations, out of scope per the plan).

## ADR-011 - Security Hub CSPM without standards, GuardDuty without Runtime Monitoring

- **What:** Security Hub CSPM is enabled to aggregate findings (GuardDuty, firewall custom findings) with no standard enabled. GuardDuty runs with EKS audit log monitoring; Runtime Monitoring stays off.
- **Why:** Security Hub controls are evaluated by AWS Config rules, which need a Config recorder billed per configuration item, outside the plan. Runtime Monitoring installs an agent add-on on every node and needs its own endpoint, on a cluster limited to 4 vCPU by the account quota.
- **Rejected:** The Foundational Security Best Practices standard with an AWS Config recorder.

## ADR-012 - Firewall rules in strict order with default drop

- **What:** One stateful rule group in strict order. Ingress: only HTTP on port 80 to the public subnets, and only for paths under `/api/`; every other port, protocol or path is dropped with a readable reason. Egress: TLS to an allowlist of domains; everything else is dropped. Policy default: drop established and alert.
- **Why:** Strict order makes the evaluation readable top to bottom, and each drop has a message that the dashboard shows as the reason.
- **Rejected:** The managed domain-list rule group for egress (its drop messages are generic).
