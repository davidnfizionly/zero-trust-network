# Architecture Decision Records

One entry per decision the project plan does not spell out: what, why, what was rejected.

## ADR-001 - EKS 1.35 for the baseline cluster

- **What:** The baseline cluster runs Kubernetes 1.35 on EKS, with the AL2023 managed node AMI. The original workload was built on 1.30.
- **Why:** EKS no longer offers 1.30 in us-east-1 (`aws eks describe-cluster-versions`, checked 2026-10-16: oldest available is 1.31, in extended support). The workload installs Istio with istioctl 1.30.2, and Istio 1.30 supports Kubernetes 1.32 to 1.36 (istio.io supported releases page). The versions in EKS standard support are 1.34, 1.35, 1.36 and 1.37, so 1.34, 1.35 and 1.36 satisfy both. 1.35 stays in standard support until 2027-03-27, so it never bills the extended-support rate during the build, and it sits inside Istio's range rather than at its edge. Amazon Linux 2 node AMIs are not published for 1.33 and later, so the node group moves to AL2023.
- **Rejected:** 1.34 (standard support ends 2026-12-02, too close); 1.36 (the newest version Istio 1.30 supports, with no margin); 1.37 (outside Istio 1.30 support); upgrading Istio at the same time (two changes to the baseline instead of one).

## ADR-002 - Partial backend configuration kept out of git

- **What:** The stacks declare `backend "s3" {}` and load the bucket name from `infra/backend.hcl`, generated by the bootstrap stack and git-ignored. The bucket name uses a random suffix instead of the account ID. Locking uses S3 native lock files (`use_lockfile`), with no DynamoDB table.
- **Why:** The repository is public from day one, and backend blocks cannot use variables, so a literal bucket name would publish an account-linked identifier.
- **Rejected:** A bucket name built from the account ID (leaks the ID). A DynamoDB lock table (an extra resource, no longer needed since Terraform 1.10).

## ADR-003 - Bootstrap stack state stays local

- **What:** `infra/backend` keeps its own state on the build machine (git-ignored). It holds only the state bucket and the budget.
- **Why:** The stack creates the bucket the others store state in. Migrating its state into its own bucket adds a circular dependency for two resources that are destroyed last.
- **Rejected:** Migrating the bootstrap state into the bucket after creation.
